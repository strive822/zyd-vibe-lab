# 已确认的工程问题

## 文本列表 Enter 触发额外按钮

现象：复制之后“更多文本”消失、设置打开，浮窗持续展开。根因：列表发出 `itemActivated` 后，Enter 继续传播到 QDialog 默认按钮。处理：对话框 Enter 只执行当前焦点按钮，列表已经完成的动作不再触发其他按钮；面板开关按事件维护锁。历史回归验证Enter只复制、不额外打开设置。2026-10-05用户改为成功后关闭列表并收回贴边球：只有成功才发出完成事件，先释放面板锁，再清除临时焦点并调用现有收起动效；失败保持列表可读、可重试。固定展开与自由放置仍保留。回归覆盖鼠标／Enter、重复打开、四边、普通与减少动效，以及失败后重试，防止成功隐藏改变焦点后误触发管理按钮。

## 记事本保存不等于进程退出

现代记事本可复用进程或保留多个标签。只观察独立文件已保存内容；保存采用原子替换时要重新挂接文件监听，删除时立即失效，不使用旧正文缓存。手动“重新读取正文”作为退路。不得依据 PID 退出判定保存成功。

## Windows 文件监听测试中的原子替换偶发失败

2026-10-03，GitHub Windows 检查在模拟编辑器保存时，`os.replace` 报 `PermissionError / WinError 5`，121 个测试通过、1 个失败。前一提交相同测试曾通过；日志没有记录占用文件的具体进程，不能直接归因于文件监听器或杀毒软件。

测试原先假定文件替换一次即可成功。模拟保存现在仅对 Windows 访问／共享冲突 5、32、33 在 2.5 秒内重试，并继续处理 Qt 事件；其他错误和持续占用仍立即或在截止时间后抛出。成功替换后清除临时文件创建期间的通知，再验证新的文件通知、保存内容、删除／重建和另一文本的独立性。

新增回归检查覆盖短暂占用、无关权限错误和持续占用超时。原生 Windows 临时文件句柄可复现同样的错误 5，定时释放句柄后保存重试成功；这证明机制，不证明云端的具体占用者。实际文件监听用例连续运行 10 次通过。日常实例、用户文件和便携包不参与这个临时目录测试；不能仅通过跳过失败测试或整套自动重跑来代替定位。

## Windows 混合 DPI 的逻辑坐标会出现屏幕间空隙

Qt 对屏幕尺寸和坐标的处理可能形成逻辑坐标上的空隙。判断多屏接缝使用 Win32 物理矩形；窗口布局仍用 DIP／工作区相对锚点。纯几何与单屏原生验证通过，混合 DPI／拔屏仍需物理设备验证。

## 停止后不能留下延迟请求

Qt 单次回调可能在 `stop()` 后才执行。数据运行层同时在定时轮询和实际请求入口检查停止标记，避免退出时创建新子进程或访问已释放网络对象。程序化休眠恢复消息回归覆盖此边界。


## 设置／取消点击／低功耗优化能分别破坏自动收起

不能把独立设置窗口可见或激活当作叶片hover锁。取消球点击不经过正常动作处理，仍需清除鼠标取得的焦点。700ms关闭尝试若被锁拒绝，解锁后需重启一次而不是每32ms不断延后。Windows非激活的mask工具窗Enter不可靠，完全停掉收起态检测会让小球无法再次展开；保留轻量轮询。用户三次悬浮移出与取消点击确认正常。

## 相对缩放倍数不等于目标DPR

原生屏幕150%时，QT_SCALE_FACTOR=1.25得到187.5%，并非125%。设置目标倍数／原生倍数，并断言Qt实际devicePixelRatio。WSL外层环境不一定传入Windows进程；在Windows子进程中设置。缩放模拟不能当成物理混合DPI验收。

## Windows venv 的python.exe可能只是启动转接器

只测venv启动PID会得到错误的低占用。性能计数应追踪其实际Python子进程和仅由应用启动的Codex后代，并用自有窗口所属PID及收起遮罩验证空闲条件。设置打开、展开、隐藏或发生交互时，不将该段记为空闲通过。

## 常用位增加后图标语义不能继续依赖旧动作编号

复制位扩展到四个后，旧编号3已是第四复制。铃铛填色、未读点、图标和Tab必须使用动作语义索引；转换图标种类前仍按实际动作检查复制反馈，避免第四复制成功把铃铛也画成勾。

## 倒计时动效需要独立帧调度和稳定的目标读数

每秒更新一次只能触发过渡首帧，不能保证160ms过渡完成；首次悬浮的详情动画碰巧补了帧，容易掩盖缺陷。使用仅在数字过渡时运行的16ms帧调度，结束、收起、隐藏或减少动态效果时停止。

GLM恢复时间有毫秒部分。每帧重新取墙上时间，会在过渡尾部跨越下一秒，前一个目标还未落定就换目标，出现每两秒跳两格。展开时250ms采样，每次动效使用同一采样时刻；只有可见格式改变才请求重绘。收起仍以1000ms检查时段规则，不维持数字帧定时器。真实Qt时钟回归在610ms起点／761ms恢复偏移复现`3594→3592→3590`，修复后为`3594→3593→3592→3591→3590`，见M6倒计时记录。

## 从Codex启动与双击启动可能读到不同AppData

环境变量字符串一致不代表文件相同。2026-10-01实际发现，工具进程的目录句柄指向Codex包LocalCache，资源管理器进程指向普通AppData；账户与文本因此落在两处，表现为新窗口未知／未更新。Path.resolve的元数据访问也不能代替读取句柄的物理路径确认。

默认数据放到USERPROFILE/.usage，升级完整复制并保留原目录；文件锁与恢复协议阻止重复实例。验证须包含资源管理器双击launch，以及已启动时再双击，而不能只在同一工具环境内启动两次。机制说明见[Microsoft MSIX文档](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes)。

## Windows 项目目录改名被占用

2026-10-02目录改为codex-usage时，A盘返回共享冲突32。浮窗退出后仍被一个失效的旧node_repl工具进程作为当前目录占用；核实其身份与工作目录并释放该工具后，原目录完整改名成功。不要因此删除重建项目或清理用户数据；移动后修正既有开机启动项、虚拟环境激活和命令入口，检查新址重复启动仍只恢复同一实例。

## 开机启动“已保存”不等于登录会话可见

2026-10-03核验发现，Codex启动上下文和Explorer桌面读到了同名Run值的不同版本。MSIX私有HKCU覆盖层中的写入、读回不能证明登录会话可见；普通子进程、新建Shell.Application及仅设置DesktopAppPolicy的进程在本机仍读到旧覆盖层。

通过既有Explorer桌面对象的Application执行固定启动项读写，并在该会话内核验。便携包登记单一usage.exe入口及同一数据目录，避免开发venv依赖和重复的长路径。构造和读取设置不登记；保存时才修改本应用的当前用户值。自动核验包括真实桌面读回、执行该命令和单实例恢复；真实重启／登录仍需用户验证。

## 窗口行为切换时整个界面卡住

页面构造和showEvent都在界面线程同步执行真实桌面启动项桥接，导致一次打开连续阻塞约4秒；保存核验也走相同同步路径。构造不再做系统读取，首次显示时将读取放入Qt工作池，保存也在后台完成，排队结果只在界面线程更新。每页仅一个进行中任务，重复切换／保存合并；失败恢复控件且不报成功。保持Explorer桌面核验，不能为了响应快而退回MSIX私有注册表视图。响应文件的短暂Windows共享锁在原10秒期限内重试，持久失败仍明确报错。原生检查需监测界面心跳和实际切页耗时，并覆盖慢读取、慢保存、保存失败与草稿保持。
